# 0001. Выбор модели процесса разработки

## Статус

Принято

## Контекст

Проект — информационная система для сети из 12 медицинских клиник,
состоящая из четырёх модулей: М1 (запись на приём), М2 (электронная
медицинская карта), М3 (отчётность для контролирующих органов), М4
(администрирование и разграничение доступа). Команда — 6 человек,
распределена между двумя городами; бюджет фиксирован, срок — 9 месяцев.

Анализ неопределённости и критичности (ЛР1) показал, что модули
принципиально расходятся по характеристикам:

- М1 — высокая неопределённость требований (заказчик прямо просит
  уточнять UX по итогам пилота), низкая критичность дефектов;
- М2 — средняя неопределённость, высокая критичность (риск для здоровья
  пациента, требования 152-ФЗ), высокая потребность в аудите;
- М3 — низкая неопределённость (формат зафиксирован приказом Минздрава),
  высокая критичность и необходимость аудита;
- М4 — средняя неопределённость и критичность, растёт по мере подключения
  новых клиник.

Единая модель процесса для всего проекта не может быть обоснованно
рекомендована: Scrum лишил бы модуль отчётности регуляторной
формальности, а V-model сделала бы невозможным быстрое уточнение UX
модуля записи на приём.

## Решение

Применяется гибридное процессное решение:

- **М2 (ЭМК) и М3 (отчётность) — V-model.** Формальная верификация и
  трассируемость требований оправданы высокой критичностью и стабильными
  регуляторными требованиями.
- **М1 (запись на приём) — Scrum.** Короткие спринты и обязательный
  Sprint Review с заказчиком позволяют быстро включать результаты
  пилотной эксплуатации в бэклог.
- **М4 (администрирование) — инкрементальная модель** с обязательным
  security-review-шлюзом перед каждым релизом инкремента (заимствован из
  дисциплины V-model), так как чисто инкрементальный подход не
  гарантирует нужного уровня проверки безопасности.

Синхронизация релизов модулей обеспечивается фиксированным
интеграционным календарём (release train) не реже одного раза в 4–6
недель, а взаимодействие между модулями фиксируется как контракт данных
(OpenAPI/JSON Schema), версионируется и проверяется контрактными тестами
при каждой интеграции.

## Последствия

**Даёт:**

- каждому модулю — модель процесса, соответствующую его реальной
  неопределённости и критичности, вместо компромиссного «одного размера
  для всех»;
- регулярную точку интеграции (release train), которая не даёт
  разъехаться модулям с разным внутренним ритмом (спринт / фаза /
  инкремент).

**Накладывает ограничения:**

- дополнительные организационные накладные расходы на синхронизацию
  разных по формальности процессов (см. риск 1, отчёт по ЛР1);
- необходимость contract-first подхода и автоматических контрактных
  тестов для API между модулями (см. риск 2, отчёт по ЛР1);
- обязательный security-review-шлюз для М4 требует выделенного
  ревьюера по безопасности на каждый релиз инкремента.

Подробное обоснование по каждой ячейке матрицы применимости — см. отчёт
по ЛР1, разделы 2–3.
